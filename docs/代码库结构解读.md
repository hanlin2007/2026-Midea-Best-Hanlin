# 代码库结构解读（2026-08-20 轻量重构后）

本文档解读 `midea_qiji_best_hanlin` 仓库中**每一个代码文件的地位、职责与入口关系**，
并说明 2026-08-20 轻量重构消除了哪些阶段递推冗余。配套阅读：
`CURRENT_BEST_PIPELINE_SZY_V4.md`（现役管线算法细节）与 `docs/lessons/`（教学课程）。

---

## 1. 一句话总览

这是一条**目标说话人语音识别**竞赛管线：唤醒音频定位目标人 → 门控判定指令音频
是否含目标人 →（接受时）MossFormer2 盲分离两路 → FireRed ASR 转写 → 触发规则决定
用原始转写还是分离通道转写。现役路线为 **szy_v4**（szy_v2 融合门控管线 + dasynth
域适配微调的 torch 分离前端）。

## 2. 分层架构（依赖只能向下）

```

┌───────────────────────────────────────────────────────────────┐

│  szy_v1/   历史管线：双 MLP 门控 + ONNX 分离 + 语速触发（休眠）  │
└──────────────┬────────────────────────────────────────────────┘
               ▼
```

规则：**只允许向下依赖**。重构前存在两处违规（szy_v1 → szy_v4 反向 re-export、
scripts → szy_v1 私有函数 `_command_features/_duration`），已修复。

## 3. 阶段递推历史与现状

| 阶段 | 门控 | 分离器 | 触发规则 | 选源 | 状态 |
|---|---|---|---|---|---|
| `midea_qiji` | ERes2NetV2 余弦 / 双 MLP | 无 | 无（无候选） | 无 | 基线，可独立运行 |
| `szy_v1` | 双 MLP（ERes2NetV2+CAM++） | ONNX MossFormer2 | 语速+关键词 | eres+cam 差分 | **休眠**（私有资产未随仓库分发） |
| `szy_v2` | 线性融合门控（6 维余弦） | ONNX 或 .pt 按扩展名 | 音色 sv_diff | ft 直接余弦 | **现役引擎** |
| `szy_v4` | 同 szy_v2（零改动） | dasynth 微调 torch 分离器 | 同 szy_v2 | 同 szy_v2 | **现役入口** |

szy_v4 与 szy_v2 的唯一差异在音频前端（配置 `moss_model` 指向 .pt 即启用），
故 `szy_v4/pipeline.py` 只是 `szy_v2.pipeline.main` 的入口转发。

## 4. 入口关系

现役入口（资产完备，直接可跑）：

```bash
bash scripts/run_szy_v4.sh            # 推荐：设置好所有环境变量
# 等价于：
PYTHONPATH=src:model/runtime/vendor MODELSCOPE_CACHE=model/workspace/midea/models/modelscope \
  python -m szy_v4.pipeline --data-root dataset/dataset_test/datasetA/datasetA \
  --jsonl dataset/.../pos.jsonl dataset/.../neg.jsonl \
  --config configs/szy_v4_firered.json --output outputs/szy_v4_submission.json ...
```

调用链：`szy_v4.pipeline.main()`（转发）→ `szy_v2.pipeline.main()` →
`SzyV2Runner.process()` 逐样本 → 门控/触发/选源 → `szy_common.reporting`
汇总写出。

历史入口（资产需自行补齐）：
- `python -m szy_v2.pipeline --config configs/szy_v4_firered.json ...`（v2 直接运行；
  v4 配置是 SzyV2Config 的合法子集）
- `python -m szy_v1.pipeline ...`（需 backend_dual.pt + ONNX Moss 模型，仓库未分发）
- `python -m midea_qiji.infer ...`（baseline：ERes2NetV2 + Qwen3-ASR，无分离）

工具入口（全部在 `scripts/`，自包含 sys.path 注入）：

| 脚本 | 入口方式 | 用途 |
|---|---|---|
| `run_szy_v4.sh` | `bash` | 现役全量运行（v4 配置） |
| `ablate_v4_pretrained.sh` | `bash` | 消融：官方预训练分离器（无 dasynth 微调）跑全量 |
| `sweep_v4_epoch_eval.sh` / `sweep_v4_gpu1_rest.sh` / `sweep_v4_sv_epochs.sh` | `bash` | 微调 epoch 扫描与 SV 重训的编排（等 GPU/等产物） |
| `check_models.py` | `python`（无参数） | 资产自检：MANIFEST.json 校验 + 残留权重扫描 |
| `relocate_workspace_models.py` | `python` | 一次性资产搬迁工具（生成 MANIFEST.json 与兼容软链） |
| `build_v4_replay_assets.py` | `python --part dataseta\|valid` | 一次性：为离线重放补 FireRed 转写资产 |
| `replay_v4_full.py` | `python --mode validate\|eval` | 离线全链路重放（验证重放器 / 评估重训 SV 快照） |
| `replay_v4_gate_ablation.py` | `python --detail ... --fusion ...` | 零 GPU 门控消融（重放任意门控变体 + oracle 上限扫描） |

## 6. 一条样本的旅程（v4 全链路）

```
pos.jsonl 一行
 → midea_qiji.infer.read_many_jsonl → Sample
 → SzyV2Runner.process:
   ① separation_paths_for     唤醒/指令 各分离出 ms0/ms1（缓存命中直接复用）
   ② transcribe_firered_rows  FireRed 转写 4 个分离通道（文本+置信度）
   ③ select_wake_anchor       唤醒文本编辑距离选锚点（一路为空回退原始唤醒）
   ④ FusionGate.score         6 维余弦特征 → 融合分 >= -0.6469？
       否 → route=fusion_reject（content 空）
   ⑤ 是 → raw 指令转写 → command_features + sv_diff → should_switch_command_timbre
       否 → route=raw（content=原始转写）
   ⑥ 是 → ft 直接余弦选 ms0/ms1 → route=moss_candidate
   ⑦ 任何异常 → raw 转写兜底（raw_fallback_error / empty_fallback_error）
 → szy_common.reporting.summarize → write_outputs
   submission.json（竞赛格式）+ detail.json（全字段）+ manifest.json（资产 sha256）
```

## 8. 命名与导入规范（请后续遵守）

1. **依赖单向向下**：scripts → szy_v* → szy_common → midea_qiji →
   third_party。禁止低层 import 高层（如 szy_v1 不得 import szy_v4）。
2. **跨模块复用的函数不加下划线前缀**；仅模块内私有的才用 `_`。
3. **重型依赖延迟导入**（torch / modelscope / onnxruntime / FireRed / peft），
   保证轻量模块可被 import。
4. 新代码从 canonical 位置导入（如文本工具用 `midea_qiji.text`）；
   `midea_qiji.infer` 的 re-export 仅为兼容历史代码与文档。
5. 冻结语义（归一化、决策规则、阈值、配置默认值）不得改动；改动后先跑
   `tests/` 再对照 `CURRENT_BEST_PIPELINE_SZY_V4.md` 的基线数字。

## 9. 注意事项

- **szy_v1 休眠**：`backend_dual.pt`（双 MLP 门控）与 ONNX Moss 模型未随仓库
  分发，v1 需要从队长工作区补齐资产才能运行；现役路线不要动 v1 阈值。
- `check_models.py` 依赖 `model/MANIFEST.json`，由 `relocate_workspace_models.py`
  在用户机器上执行搬迁后生成（不在仓库内）。
- 运行需要 torch（CUDA 版）+ modelscope + onnxruntime-gpu + kaldi_native_fbank
  （vendor 内为 py3.10 编译版），详见 `SETUP_本地复现指南.md`。
